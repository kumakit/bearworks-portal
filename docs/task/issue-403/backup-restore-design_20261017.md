# Issue #403 バックアップ・復元の受入設計

作成日: 2026-10-17 JST。稼働DBを SQLite にする場合の**設計案**。保存先・権限・費用・保持世代は未確定で、本番ファイルや外部サービスには変更を加えていない。

## 退避の流れ

1. 公開領域外の SQLite に対し、SQLite のバックアップ API で一貫した複製を一時ファイルに作る。DB本体だけを直接コピーせず、WAL の未反映分を失わないようにする。
2. 複製を読み直し、`integrity_check`、`foreign_key_check`、スキーマ版、対象時間の `[開始, 終了)`、状態別の行数、採用値と観測履歴の関係を確かめる。
3. UTC 時刻を含む上書きしない名前で保存する。検証済みの複製と、形式版・作成時刻・バイト数・ファイルの SHA-256・時間範囲・状態別行数・採用値と改訂履歴の正規化ハッシュを含む目録を一組で保存する。目録にはゾーン識別子、認証情報、HTTP リクエストの実数を出さない。ハッシュは偶発的な破損の検出用であり、悪意ある差し替えの防止は権限分離で扱う。
4. 保存先での受領とサイズを確認し、失敗時は「最新の成功した遠隔バックアップ時刻」を更新しない。最新成功が復旧目標を超えて古くなる前に通知する。稼働DBや既存収集の成功とは別状態として扱う。
5. 別の場所へダウンロードし、目録のサイズ・SHA-256を照合してから SQLite として開く。`integrity_check`、`foreign_key_check`、スキーマ版、時間範囲、状態別行数、採用値・改訂履歴の正規化ハッシュを目録と比較する。元のDBがまだある演習では元とも比較する。復元したコピーで読取りと1件の合成書込みを試し、元のDBに触れない。

初回の合成試験は、正常値、正当な0件、欠測、遅延改訂、確定値、回復不能、不正応答の各状態を含める。同じ観測の再実行は増えず、異なる有効な観測は改訂として残ることを確認する。複製を意図的に切り詰めた試験では、目録照合または SQLite 検査で復元を拒否する。**現行の容量測定は上記の復元・破損試験の合格証拠ではない。**

2026-10-17 に[仮スキーマの復元試験](verify_synthetic_restore.py)を、Git 対象外の合成DBだけで実施した。別パスにコピーしたバックアップのファイル・内容ハッシュと SQLite 整合性、読取り・ロールバックする書込み、1バイト切り詰めたコピーの拒否はいずれも PASS。これは**ファイル転送や実スキーマ、欠測・改訂の状態を含む本番復元試験ではない**。上記の全状態を使った受入試験と外部保存先からの復元は未実施。

## 保持と権限

稼働DBの「1年間」は、直近の完了 UTC 正時から遡る**365日間を保持する案**とする。開始境界を含み、境界より古い時間を削除する。閏日をまたぐ場合でも常に8,760時間で、暦上の「前年同日」とは最大1日ずれる。これは提案であり、利用者要件と照合して確定する。削除直前・境界ちょうど・削除直後の合成時間で検証し、欠測や改訂も同じ時刻基準で扱う。

バックアップの世代は別に決める。暫定案は**直近48時間の毎時版と、直近30日の各日版**を残すもの。上限は概ね78世代で、毎時バックアップが成功すれば履歴損失の目標は約1時間となる。古い日次版には稼働DBから削除済みの時間が最大約30日残り得るため、厳密に365日で全コピーから削除する要件があるなら、この案は使わず保持規則を変更する。停止した端末・失効した認証・保存失敗があれば目標を満たせないので、実運転と復元演習で判定する。

仮の[容量測定](storage-options-and-sizing_20261017.md)を78世代すべてに単純に掛けると、観測1/4/72行毎時の例でそれぞれ約63 MB / 182 MB / 3.0 GB。これは満杯になった1年DBの非圧縮コピーが全世代にあると仮定した概算であり、目録、サービス側の版管理、転送、他の保存物、安全余裕は含まない。最終的な世代数と費用は、実装スキーマで測り直して決める。

保存先がオブジェクトストレージなら、稼働インスタンスの主体は専用バケットへの新規作成と必要な確認だけを許し、過去のオブジェクト・バケットの削除を許さない。古い世代の削除は別の管理権限または事前に検証したライフサイクル規則に分ける。Drive には同等の自動ライフサイクルがないため、別の削除主体・期限管理を実装し、残容量を監視する。稼働DB、WAL、SHM、バックアップ一時ファイルは公開領域外に置き、サービス利用者以外の読取りを拒否する。保存先の非公開設定・権限・作成/読取り/削除の可否を実設定から読み戻す。

## 本番保存の前に通す条件

1. **候補の選定前**: 候補の容量・料金・権限・認証の更新方法を読み取り確認する。観測結果から決めた暫定スキーマで1年分の合成データを測り、世代上限と余裕を含む容量帯を見積もる。残る障害領域も比較して選ぶ。
2. **選定後、外部書込みの承認後**: 選んだ保存先の権限・費用条件を確かめ、小さな合成ファイルを保存・取得・照合する。読み取り調査の承認だけで外部への試験転送は行わない。
3. **本番保存の有効化前**: 確定した実装スキーマの合成データで容量を再測定し、別パス復元と破損試験を通す。選んだ外部保存先へ同じ合成バックアップを転送し、別パスへ戻して整合性と内容を照合する。実容量・世代数・他の使用量を加え、上限と費用を再確認する。

## 本番保存の開始後に通す条件

- 初回の本番バックアップから別パス復元を確認し、それまでは「初回復元未確認」と扱う。成功したバックアップがない状態を正常運用と表示しない。
- 次の定期バックアップも成功し、最新成功時刻と失敗通知が動作することを確認する。
- 最大損失約1時間・24時間以内の復旧は、定期運転と復元演習結果を見て最終決定する。実証前に達成済みとは報告しない。
