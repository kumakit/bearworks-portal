# Issue #403 Phase 0 追加の読み取り確認

確認日: 2026-10-17 JST。対象は既存 Apps の Cloudflare Free ゾーン全体と OCI 収集環境。認証情報、ゾーン識別子、HTTP リクエストの件数や個別データは、この記録に含めない。本番ファイルや設定は変更していない。

## 時間別値の再照会

[読み取り専用プローブ](probe_repeated_hours.py)を既存 OCI の Python 環境で標準入力から実行し、リモートへファイルを保存しなかった。対象は**`httpRequestsAdaptiveGroups`**。完了した UTC 正時から1、6、24、168、696時間前の各1時間を、固定した期間で続けて2回ずつ照会した。168・696時間前の成功は、約3日しか遡れない `httpRequests1hGroups` の証拠ではない。

| 観測項目 | 結果 |
| --- | --- |
| 有効な照会の組 | 5/5 |
| 直後の再照会で `count` が変わった組 | 0/5 |
| 直後の再照会で `sampleInterval` が変わった組 | 0/5 |
| 少なくとも一方に抽出がある組 | 3/5 |

この結果は**Adaptive の数秒間の再照会が同じ値だった**ことだけを示す。選択した1時間集計の数時間・数日後の遅延更新や抽出の揺れは未確認であり、時間別値の採用・凍結規則はまだ決められない。

現行の公開データは各時間の `sampleInterval` を持たない。このため、公開時と後の再照会で件数が一致しても抽出条件まで同じだったとは判定できない。調査用プローブはこの制限を結果に明示する。

既存の公開 `data.json` の30日ブロックは確認時に `PARTIAL / INCOMPLETE / PARTIAL_RESPONSE` で、過去の値を含まず、直前の公開値との比較には使えなかった。同じ720時間の範囲を1回の独立照会で再取得すると、時間別720行、欠け・重複0、全体値との一致が得られた。この1回の再照会成功を定期収集の復旧証明とは扱わない。その後に正常公開されたブロックとの比較結果を下に記す。

その後の毎時収集では次を確認した。時刻は日本時間。比較はすべて同じ `[開始, 終了)` を使い、出力は変化した時間数と状態だけに限定した。

| 確認時刻 | 公開済み30日ブロック | 同じ範囲の再照会 |
| --- | --- | --- |
| 15:56 | 正常 | 720時間のうち期間末尾の1時間だけ件数が変化。全体合計も変化 |
| 16:01 | 16:00終了の新ブロックは一部取得 | 720時間は揃うが、時間別の和と独立した全体値が不一致 |
| 16:04 | 公開済みブロックは一部取得のまま | 再照会では720時間が揃い、時間別の和と全体値が一致 |

**収集直後の30日照会には利用不能な場合がある**ことを示す。何分待てば常に安定するかは未確認。Cloudflare の[同じクエリの結果が変わる理由](https://developers.cloudflare.com/analytics/faq/graphql-api-inconsistent-results/)には Adaptive の抽出条件の変化も挙げられているため、この差をデータ到着の遅れだけに帰さない。既存収集の実行時刻や再試行は、別途修正を計画する。

同じ直近24時間を `httpRequests1hGroups` と `httpRequestsAdaptiveGroups` で照会すると、双方とも24時間が揃ったが、時間別値は23/24時間で異なり、全体の和も異なった。前者には抽出行がなく、後者には19行あった。**異なる2つのデータセットを同じ履歴・比較の数値として混ぜない。** 長期履歴をどちらで作るか、現行30日グラフとの整合を含めて再レビューする。

## 保存先・バックアップ

OCI 上ではルート用と追加のデータ用の2つのディスクが見えた。追加ディスクは**同じインスタンス上**にあり、独立したバックアップ先の合格証拠にはならない。既存の退避用 private directory も Cloudflare 履歴用の独立バックアップとは確認できない。OCI 上の ubuntu 利用者環境には OCI CLI と標準位置の CLI 設定は見つからず、Object Storage 等の実在・権限・費用は確認できていない。

候補として OCI Object Storage を調べた。[Oracle の Always Free 説明](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)には、Always Free のみのアカウント向けに Object Storage 計20 GB、月50,000 API リクエストの枠が記載されている。ただし、**このアカウントの区分、利用可能な残量、既存のバケット、必要な権限、実際の費用は未確認**。稼働インスタンスとは別サービスの候補だが、同じ事業者・地域の障害まで分離できるとは主張しない。新しいバケットや権限の作成はこの読み取り調査に含めない。

次は、時間を置いた同一時間の値の比較と、稼働インスタンスと異なる障害領域で利用可能な保存先・保持期間・復旧経路を確認する。後者が確定しなければ本番保存は開始しない。

## 調査後の要件決定

利用者は、まず1年間、`httpRequests1hGroups` の時間別値を履歴として保存する方針を選んだ。現行30日グラフの Adaptive 値とは混ぜず、1時間集計の履歴が揃ってから30日グラフも切り替える。これは要件の決定であり、上記の読み取り結果や本番実装の証拠ではない。

[1時間集計用の読み取り専用プローブ](probe_1h_stability.py)を、既存 Apps の Python 環境で標準入力から実行した。公開済みの正常な24時間ブロックと**まったく同じ UTC 期間**を `httpRequests1hGroups` で再照会し、時間別件数の差だけを集計した。リモートに調査ファイルは保存していない。

| 観測項目 | 2026-10-17 20:15 JST の結果 |
| --- | --- |
| 公開期間の終了から再照会まで | 約16分 |
| 24時間の行数と時刻境界 | 双方とも24時間、有効 |
| 値が変わった時間 | 1時間だけ。期間末尾の1時間 |
| 再照会時に抽出された行 | 0 |

これは選択した1時間集計でも**公開後に直近時間の値が変わり得る**証拠である。値が何分・何時間後に安定するか、24時間より古い行が後から変わるかは、この1回の比較では未確認。前述の Adaptive 30日照会の変動とは別に扱う。保存時は短い重ね取りと値の改訂を想定し、凍結時間を実測後に決める。

## 取得期限と別集計との差の追加確認

2026-10-17 20:42 JST 頃、[境界確認プローブ](probe_1h_boundary.py)を同じ既存環境で標準入力から実行した。現在の UTC 正時から70～75時間前に始まる各1時間について、`httpRequests1hGroups` の可否だけを出力した。

| 時間の開始が UTC 正時から何時間前か | 結果 |
| --- | --- |
| 70・71・72時間 | 有効な1行を取得 |
| 73・74・75時間 | GraphQL エラー |

今回の正時からの照会では72時間前まで取得できた。実行時刻は正時から約42分後なので、時間の**開始時刻**からの経過は表の数字より約42分長い。Cloudflare 側の判定が現在時刻と時間境界のどちらを基準にするかは、この1回だけでは断定できない。再実行や照会範囲の変化で境界が変わる可能性を残し、運用上の安全余裕を設ける。

同時刻頃、[データセット比較プローブ](probe_repeated_hours.py)で直近の完了24時間を双方から再照会した。24行ずつ揃い、1時間集計は抽出0行、Adaptive は20行が抽出あり。24時間中23時間の値が異なった。1時間集計を分母にした各時間の差の絶対値は中央値1.6%、最大15.2%、24時間合計の差の絶対値は2.5%。方向や生の件数は記録していない。この単発の差を全期間へ一般化せず、非公開の比較期間でも分布を観測する。

## 時間差観測の締めくくり（2026-10-20）

予定していた 21:00 JST の確認を実施し、自動追跡を停止した。Git 対象外のローカル記録を[集計スクリプト](summarize_1h_snapshots.py)で読んだ。期限前の29回と、期限約43分後の締めくくり1回で計30回のスナップショットがあり、同じ時間の隣接再照会2,015組に件数・`sampleInterval` の変化は見つからなかった。抽出を示す行も見つからなかった。これは **HTTP リクエストの実数ではなく、観測回数と変化回数**である。生の値はローカルの非公開フォルダーにのみ残し、この文書には載せない。

ただし、2時間を超える取得間隔が5回あり、最長は約14.8時間だった。1時間の終了後0～1時間内に行った隣接再照会は3組のみで、しかも同じ72時間窓を重ねて見ているため、独立した実験ではない。約16分後に公開済みの末尾時間の値が変わった先の実測は、この連続観測より前に起きた。今回の「変化なし」はその事実を否定せず、観測空白で生じて戻った変化や、取得期限を越えた後の改訂も検出できない。

したがって、**何分・何時間後なら値が必ず安定するかは未確定**。ここから即座に値を凍結する時刻を決めたり、「抽出は常にない」と扱ったりしない。設計では、最初の有効値を仮値とし、同じ時間の有効な再照会が変化した場合は改訂履歴を残す。部分・不正・期限切れの応答で有効値を上書きしない。取得可能な期限内は改訂を受け入れる案を検討し、画面に出す「確定」の条件、重ね取りの幅、取得不能前の通知期限は追加の狙いを絞った観測とレビューで決める。
