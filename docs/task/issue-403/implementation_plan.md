# Issue #403 Cloudflare アクセス履歴と30日間の前期間比較 — 計画案

作成日: 2026-10-17 JST

正本: https://github.com/kumakit/mission-control/issues/403
前段: https://github.com/kumakit/mission-control/issues/397

## 目的と境界

ゾーン全体の HTTP リクエストについて、検証済みの時間別集計を保存し、直近の完了した30日間と、その前の完了した30日間を同じ条件で比較する。現在の30日表示、24時間・7日間の比較、国別表示、Firewall 参考表示、Digest の必須監視を維持する。

IP アドレスや個人単位の記録、Firewall イベントの履歴、危険度判定は対象外。診断ログの保存期間保証も別の運用課題とする。有料プラン・新たな有料サービス・WAF / Access / DNS 設定変更は前提にしない。

## 確認済みの現状

- Issue #397 の実測では、30日アクセス集計に使う `httpRequestsAdaptiveGroups` の遡及上限は約31日。現行30日は取得できるが、その前の30日まで API だけで直接取得できない。7日・30日の時間別値には抽出による推計が含まれ得る。
- Apps は完了した UTC 正時を終端に、現行30日の720時間と同じ条件の全体値を照合する。Portal は現行30日を表示し、前期間はまだ選ばない。現行の `data.json` は出力時に置き換わり、比較用の保存履歴ではない。
- Phase 2 の記録は30日比較を NO-GO とし、履歴保存を別フェーズとした。2026-10-17時点で、比較に使える連続60日分の保存履歴があるという証拠はない。

参照: [Phase 0 の実測](../issue-397/phase0-evidence-status_20261011.md)、[Phase 2 の実測](../issue-397/phase2-evidence-status_20261012.md)、[Phase 2 の実装記録](../../history/20261012_issue#397_phase2_walkthrough.md)。

## Phase 0: 保存方式を決める前の読み取り調査

1. Apps 本番の収集間隔、実行権限、出力先、既存の永続領域、空き容量、バックアップと復旧方法を調べる。保存先を選ぶ際は、費用、障害時の復元、同時実行、権限、運用負担を比較する。候補は既存 OCI 上の小規模 DB と既存の保存方式を優先し、新サービスの導入は必要性を示してから判断する。
2. 初期の30日分を API から取得して保存できるか、設定と小規模照会で再確認する。過去60日分を取得できるとは仮定しない。初期値の取り込みに成功しても、前期間比較の公開は連続した必要期間が実際に揃ってからとする。
3. 現行30日窓が毎時ずれる点を踏まえ、保存単位を決める。候補は「検証済みの時間別バケット」と「検証済み30日窓のスナップショット」。同じ1時間が後の収集で異なる値・抽出率になったときの採用規則、再実行時の重複排除、遅延確定、欠損の修復条件を定義する。異なる抽出条件の値を無言でつなぎ合わせない。
4. 最低60日間の比較対象を保持するための余裕期間、期限切れデータの削除時点、バックアップ対象、復旧検証を定める。実際の保存開始日と比較可能になる見込み日は、実測後に示す。

## 実装案（Phase 0 とレビュー後に確定）

1. Apps に履歴保存を独立した任意機能として追加する。既存の検証を通ったアクセス系列だけを保存し、出典、対象範囲、UTCの時間境界、APIが返した値、抽出の状態、取得時刻、契約版を記録する。不正・部分取得・期限切れの値で有効履歴を上書きしない。書き込みは原子的に行い、同時実行と再実行に耐える。
2. 比較器は `[開始, 終了)` の完了した UTC 正時で30日×2を検証する。各期間720時間、重複・欠けなし、同じゾーン・データセット・フィルタ・集計単位・比較可能な精度区分であることを要求する。APIの `count` を再乗算しない。抽出を含む比較は推計値どうしの参考比較と明記する。条件を満たさない場合は割合や差分を出さず、理由を返す。
3. Portal へは比較結果とその可否・理由を独立した任意ブロックとして渡す。履歴保存を開始した後だけ「蓄積中」と表示し、両期間が揃えば30日間の前期間比を表示する。失敗時は現行30日のグラフ・地図を残す。Digest の必須10項目には追加しない。
4. Apps の保存を先に有効化し、バックアップと復旧を確認する。履歴が揃うまでは Portal の比較表示を無効のままにする。Portal の受信側を配備した後、実データで条件が成立した時点に限り表示を有効化する。

## 検証と受入条件

- 59日23時間、ちょうど60日、途中欠測、重複、再実行、遅延更新、期間境界、推計区分の不一致、部分応答、保存失敗、復旧後を合成データで検証する。
- Apps と Portal の契約テストで、履歴・比較ブロックの欠落、不正、期限切れが既存のアクセス表示と Digest の判定に波及しないことを確認する。
- 本番では保存開始、定期書き込み、バックアップ、復旧手順を別々に確認する。60日分が揃うまで30日比較を受入済みとしない。
- 認証済み PC / スマートフォンで、比較の対象期間、HTTP リクエスト数、推計の注記、比較できない理由が分かることを確認する。

## 未決定事項とレビューゲート

保存先、保持期間の余裕、後から変わった時間別値の採用規則、抽出率が異なる2期間の比較可否、バックアップ・復旧の責任を Phase 0 の証拠で決める。これらはデータの意味と運用費に直結するため、Apps/Portal の実装前に手動の計画レビューを受ける。レビュー後も、保存の本番有効化と比較表示の公開は別々に判定する。

## 戻し方

比較表示に誤りがあれば Portal の比較機能だけを無効化し、現行30日グラフを維持する。保存で障害や想定外の費用が出た場合は Apps の任意保存を停止し、既存収集・Digest の経路を維持する。保存済みデータは調査・バックアップ方針に従って扱い、無断で消去しない。
