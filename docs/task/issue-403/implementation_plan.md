# Issue #403 Cloudflare アクセス履歴と30日間の前期間比較 — 計画案

更新日: 2026-10-21 JST

## 2026-10-21 方針変更：履歴収集を先行

利用者は個人用の履歴について、独立バックアップを本番保存開始の条件から外し、時間別履歴の収集を先に始めることを選んだ。本節は以下の「実装前に追加する読み取り調査」「バックアップ」「未決定事項とレビューゲート」にある開始前条件を、この第一段階に限って置き換える。バックアップ・復元設計は後続作業として保持し、完了済みとは扱わない。稼働DBを失うと履歴を失い、30日比較に必要な期間をため直す可能性がある。

第一段階は Apps の保存のみ。公開 Web 領域外の SQLite に、ゾーン全体の `httpRequests1hGroups` の完了した UTC 時間を365日間保持する。現在の `data.json`、Portal のグラフ、Digest の必須判定は変更しない。保存は既定で無効の独立フラグを設け、既存の公開に成功した後に実行する。失敗時は既存収集の成功・終了コードに影響させず、生件数・認証情報・ゾーンIDをログに出さない。

取得可能な範囲内で完了時間を重ねて再取得する。初回の有効値を仮値とし、後続の有効値が変われば改訂する。抽出の有無、初回・最終確認時刻を保持し、不正・部分応答や欠測で有効値を上書きしない。有効な0件と欠測は区別する。有限回の観測で普遍的な安定時刻は証明できないため、固定した凍結時刻を開始前条件にしない。取得期限後の値は最終観測値として保持するが、正確性を保証した「確定値」とは呼ばない。30日グラフ切替・前期間比の公開条件は、保存開始後の実データを確認して別に決める。

開始前に、非公開パス・権限・DB容量、重複実行、欠測、改訂、抽出、0件、破損・ロック時の既存収集からの隔離を合成データで検証する。バックアップ未実施を運用上の残余リスクとして記録する。新規課金・権限拡大は行わない。Apps の push と本番反映は共通の明示承認ルールに従う。

## 目的と境界

ゾーン全体の HTTP リクエストについて、`httpRequests1hGroups` の検証済み**時間別履歴をまず1年間保存**する。将来の長期グラフで時間別の変化を見られる形にし、直近の完了した30日間と、その前の完了した30日間の比較にも使う。長期グラフの画面そのものはこの段階では作らない。現行表示と収集を維持しつつ、30日グラフは同じ1時間集計の履歴が揃った段階で切り替える。24時間・7日間の表示、国別表示、Firewall 参考表示、Digest の必須監視を維持する。

IP アドレスや個人単位の記録、Firewall イベントの履歴、危険度判定は対象外。診断ログの保存期間保証も別の運用課題とする。有料プラン・新たな有料サービス・WAF / Access / DNS 設定変更は前提にしない。

## Phase 0 の確認結果（2026-10-17）

- Issue #397 の Free 実測では、30日集計に使う `httpRequestsAdaptiveGroups` の遡及上限は約31日、1回の照会上限は30日。30日間の前期間を API から直接取得できない。7日・30日の値は抽出による推計を含み得る。過去の実測では30日系列の720時間が検証を通った。全体値は時間別値の単なる合計ではなく、同じ条件の独立した照会で取得し、時間別の和と毎回照合する。API は各行の `sampleInterval` を返す。
- Apps 本番の収集は毎時 UTC 正時に起動する。動作中の収集・出力・契約のコードは手元の調査対象と一致した。現行の `data.json` は収集のたびに置き換わり、比較に使える履歴ではない。Portal の30日比較欄は現在、前期間の値を受け取らない。
- OCI 上の現在の配信先は公開 Web 領域にある。履歴の保存先には使わない。既存の Python には SQLite が利用可能で、ディスクには調査時点で約30 GB の空きがあった。これは1年間の運用容量や復旧可能性を保証する数字ではない。
- Digest には非公開の「最終成功」状態と原子的な書き込み手順があるが、Cloudflare 履歴のバックアップではない。新しい履歴について、バックアップ先・周期・復旧実績は確認できていない。
- Adaptive の追加読み取り照会では、5つの時間をそれぞれ直後に再取得した値は同じだった。この5組は選択した1時間集計の安定性の根拠にはしない。公開済み30日ブロックが一部取得だったため、その値との比較はできなかった。同じ範囲の単発再照会では720時間が揃ったが、定期収集の復旧を意味しない。
- 後続の毎時収集では、正常公開された30日窓を約1時間後に再照会すると末尾1時間の値が変わった。次の収集直後は720時間が揃っても時間別の和と全体値が不一致で、約4分後の再照会では一致した。直後の一部取得を遅延到着だけでなく Adaptive の抽出の揺れとしても扱い、収集時刻・再試行条件を見直す。
- 同じ24時間で `httpRequests1hGroups` と `httpRequestsAdaptiveGroups` を比較すると、時間別値は23/24時間で異なった。前者はその実測で抽出なし、後者は19行に抽出あり。両者を同じ比較の数値として混ぜられない。
- OCI には別のデータディスクもあるが、稼働インスタンスと同じ障害領域にある。独立したバックアップ先はまだ確認できていない。
- 利用者が OCI Console で Japan East (Tokyo)・ルートのバケット一覧0件を確認した。選べたコンパートメントはルートのみ。既存バケットはこの表示範囲にないが、アカウント区分・作成権限・料金・インスタンスからの書込権限は未確認。
- 同じ Console のコスト分析では対象期間0円、サブスクリプション詳細は項目なし・現在料金 $0.00。Always Free の表示例とは整合するが、区分の明示がないため未確定とする。新しい保存先が無料になるという判断には使わない。
- 利用者は、30日比較用の合計値だけでなく長期グラフ用の時間別履歴も保存し、期間はまず1年間と指定した。
- 利用者は、履歴の出典を短期の `httpRequests1hGroups` に決め、30日グラフも履歴が揃ったら同じ出典へ切り替える方針を選んだ。これは要件の決定であり、保存・切替が実施済みという意味ではない。

- 同日の単発境界照会では、UTC 正時から72時間前に始まる1時間を取得でき、73時間前は GraphQL エラーになった。同じ完了24時間のデータセット間の差は、時間別の絶対差の中央値1.6%、最大15.2%、合計の絶対差2.5%だった。いずれも一時点の値で、将来の境界や差の保証ではない。

## 保存するデータと30日比較の作り方

履歴と30日グラフ・比較には、利用者が選んだ `httpRequests1hGroups` だけを使う。現行30日グラフの `httpRequestsAdaptiveGroups` と値を継ぎ足したり、両者で前期間比を計算したりしない。今回の24時間実測では1時間集計に抽出行がなかったが、将来も常に抽出なしとは決めつけず、返却された抽出情報を保存する。

1. **1時間の履歴**: Apps は完了済み UTC 正時の `sum.requests` と `avg.sampleInterval`、時間境界、取得時刻、時間終了からの経過時間、ゾーン・データセット・フィルタ・集計方法・契約版を公開領域外の SQLite DB に保存する。現行コードと読み取りプローブは `avg.sampleInterval` の返却と数値型を確認している。IP や個別リクエストは保存しない。1時間ごとの状態は「未収集」「有効な仮値」「確定値」「欠測・回復待ち」「回復不能」「保存失敗」を分け、**有効な0件**を欠測と区別する。現行の24時間 parser は24行を必須にするため、履歴用の検証を別に設けるか、安全に一般化する。保持期間はまず1年間とする。
2. **重ね取りと欠測回復**: 毎時、完了時間を重ねて照会し、収集失敗や後から変わる値を短い保持期間内に回収する。1回の照会上限72時間、遡及上限約73時間は別の制約として扱う。実測で求める安全な遡及幅を `L`、確定までの待ちを `W`、照会間隔を `T`、境界・障害用の余裕を `S` とし、回復可能な障害長の上限を `L − W − T − S` 以下と見積もる。`L` は照会上限72時間を超えず、API の正確な境界を確認するまで仮値にしない。重ねる範囲・再試行・欠測通知の期限はこの上限に収まるよう決め、通知は少なくとも回復不能になる前、目安として回復可能時間の半分以内に出す。期限を越えた欠測をゼロで埋めず、回復不能として残す。保存開始前の30日間は API から復元できない。
3. **採用値と改訂**: 「観測履歴」と「画面・比較に採用する1時間1行」を分ける。観測の出典と差を追跡し、同じ観測の再実行は増やさない。同じ値の再確認は最終確認時刻を更新し、不正・部分取得・期限切れの観測で有効値を上書きしない。識別キーと重複排除方法、凍結までの時間、凍結後に変化した場合に維持・改訂・凍結延長のどれを選ぶか、改訂履歴の上限を時間差の実測で決める。**この規則が決まるまで履歴保存の実装へ進まない。** `sampleInterval > 1` の行は推計として保持し、正確な行と混ざる場合の採用・表示条件も実測後に決める。
4. **30日グラフへの切替**: 末尾を「最新の確定値の次の UTC 正時」に揃えた `[開始, 終了)` の720時間すべてに、同じ出典・契約の確定値があり、合計を検証できたときだけ30日グラフ全体を履歴へ切り替える。許容欠測は0時間とし、1時間でも回復不能な欠測があれば、その時間が窓から外れるまで最大30日切替を見送る。旧 Adaptive グラフと履歴の一部を混ぜない。24時間は現行の1時間集計、7日間は現行 Adaptive のまま。24時間の未確定な末尾と履歴の確定値が一時的に違い得ることを期間説明に含める。7日グラフの出典変更は別判断とする。
5. **前期間比**: 現在と直前の30日を、末尾を確定済みに揃え、境界が隣接する UTC 正時の720時間ずつで組み立てる。両窓の計1440時間の許容欠測は0時間。1時間でも回復不能なら、その時間が窓から外れるまで最大60日比較を見送る。ゾーン・データセット・フィルタ・集計方法・契約版・採用値の品質が比較可能な場合だけ、同じ履歴の合計から差と割合を出す。抽出行の扱いが決まるまで推計を含む窓は比較不能とするが、抽出頻度によってこの条件を再検討する。異なる出典の独立合計を照合条件に混ぜず、保存前の元データ検証と履歴からの再計算を検証する。欠測や品質不一致なら理由を返し、古い比較値を代用しない。

30日グラフの切替には少なくとも約30日、前期間比には少なくとも約60日の有効履歴が要る。API の短い遡及上限内で初期に取り込めた分を除き、それ以前は復元できない。日付だけで公開せず、実際に720時間・1440時間が揃ったことをそれぞれ確認する。国別の30日表示は現行 Adaptive の別集計として維持し、地図の割合はその国別集計内の母数で求める。画面には「国別表示は別の集計方法を使うため、グラフの合計と異なる場合があります」と示す。切替日と「集計方法の変更により、以前の30日表示と数値が異なる場合があります」も示す。

## 実装前に追加する読み取り調査

既存の認証主体で、`httpRequests1hGroups` の**固定した同じ完了時間**を、終了後およそ5・15・30・60分、3・6・12・24・48・60時間に少量ずつ再照会する。異なる時刻帯の複数の時間を対象にし、特に今回不足した完了直後の観測を優先する。各照会の予定時刻と実行時刻を記録し、実行できなかった間隔も集計する。`sum.requests` の差と割合、`avg.sampleInterval` の型・値・抽出頻度、最後に変化した時点を調べる。約16分後に末尾1時間が変わった実測があるため、初回値を無条件に凍結しない。70～75時間前の境界を1時間刻みで複数回確認し、遡及上限の起点と照会上限72時間の両方を検証する。保持期限の外に出た時点は失敗を予期し、無理な反復照会をしない。個別リクエストや認証情報・生の件数は共有証跡に記録せず、分布と変化回数だけを残す。観測だけで恒久的な安定を証明できないため、保存設計は初回値を仮値とし、取得可能な期間の有効な変化を改訂履歴として残す案を基準にする。画面へ採用する時刻、重ね取り・通知の余裕、取得期限後の扱いは、追加観測とレビューを経て決める。元データの再現性が確認できない場合は、比較と長期グラフの数値公開を保留する。

現行30日 Adaptive 窓が毎時の収集直後に一部取得となる条件を切り分ける。これは切替前の表示と7日・30日の国別表示に関わる #397 側の問題として追跡し、#403 の履歴保存だけで直ったとは扱わない。#397 の収集時刻・再試行の修正は別変更とし、#403 の履歴処理をそれに依存させない。1時間集計と Adaptive の同じ期間の時間別・合計差は割合の分布を出し、画面の説明文と切替判断に用いる。

稼働中の履歴DBは、既存 OCI インスタンスの公開領域外に置く SQLite を第一候補とする。Google Drive はファイル保管なので稼働DBには使わない。BigQuery は時間別行の保存・集計に使えるが、重複排除・改訂・権限・復元・課金を別設計する必要があるため、今回は選定を保留し、将来の分析需要が明確になった場合の代替案とする。課金なしの [BigQuery Sandbox](https://docs.cloud.google.com/bigquery/docs/sandbox) はテーブル等が60日で失効するため、1年保持の候補にならない。

**独立したバックアップ先**は OCI Object Storage、Google Drive、Google Cloud Storage、別端末への定期取得を比較する。OCI は既存運用との接続が簡潔だが、同じ事業者・地域の障害は分離できない。Drive はファイル世代を置ける一方、[個人アカウントの最大15 GBを Gmail・写真と共用](https://support.google.com/drive/answer/9312312)し、定期保存にはユーザーの OAuth 認証・失効時の復旧が必要。サービスアカウントは個人の My Drive に自分の容量でファイルを所有できず、[共有ドライブかユーザー代理の OAuth が必要](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)。Google Cloud Storage は別事業者の保管先になるが、[無料の月5 GBは米国の指定リージョンだけ](https://cloud.google.com/storage/pricing)なので、東京保存・通信・課金設定を含めて見積もる。別端末案は端末の稼働・取得失敗通知・保持期間・復旧担当を確認する。どの候補も保存場所、認証と権限、実際の空き容量、世代保持と削除、費用、定期運転、別の場所への復旧演習で判定する。独立先が確定しなければ本番保存へ進まない。新しい権限・課金設定・費用が必要なら別途判断する。

Object Storage を選ぶ場合の案は、東京リージョンの専用・非公開バケットを作り、SQLite のバックアップ API で取得した整合した DB を、毎回異なる時刻付きの名前で送る方式とする。稼働インスタンスには当該バケットへの作成・必要な確認だけを許し、既存オブジェクトやバケットの削除権限を与えない。復旧用の読取権限は別に設計する。保存時暗号化、版管理・保持期限、古い世代を消す主体と条件、容量上限、失敗通知を決め、変更後の実設定を読み戻す。東京の Compute とはサービスを分けられるが、地域全体の障害や同じ OCI アカウントの障害は分離できない。無料枠はアカウント区分と使用量を確認し、[Oracle の説明](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)にある枠内と**実測で**判断する。版管理では旧版も容量を使うため、無条件に有効化しない。

Google Drive または Google Cloud Storage を選ぶ場合も、SQLite のバックアップ API で作った整合したファイルを、上書きしない時刻付き名で転送する。アップロード結果の確認に加えて、別の場所へダウンロードし、SQLite の整合性・時間範囲・採用値の照合を行う。Drive は共有容量と再認証、Cloud Storage は Google Cloud プロジェクトの権限・請求・リージョン・転送量を確認する。いずれもファイルが見えるだけでは復旧可能と判定しない。

容量は、保持期間を365日と定義するなら採用値が8,760時間分という行数だけ先に計算できる。暦年単位で閏日を含むなら8,784時間分になるため、保持期間の定義も確定する。観測・改訂の保存量、索引、SQLite の WAL、バックアップ世代はまだ不明。重ね取りした72時間を毎時すべて新規観測として保存すると、通常の毎時実行だけで約63万行/年にもなるため、同一観測の重複排除キーと改訂上限を先に決める。**保存先の候補を絞る前**に、観測結果に基づく暫定スキーマと改訂上限で1年分の合成 DB を測り、世代数・余裕・既存使用量を含めた容量帯を見積もる。**本番保存を有効にする前**に、確定した実装スキーマで再測定し、選定先の実際の枠・費用と照合する。仮の小さい DB サイズだけで課金や本番運用を判断しない。

初回の[仮スキーマ・合成データによる測定](storage-options-and-sizing_20261017.md)では、365日分の整合したバックアップ1世代は観測行が1/4/72行毎時の場合に約0.81/2.34/39.00 MBだった。これは最終スキーマや実際の改訂頻度を表さず、保持世代・既存使用量を含まない。保存先の選定根拠にする前に再測定する。

[バックアップ・復元の受入設計](backup-restore-design_20261017.md)では、上書きしない世代、破損検出用の目録、別パスへの復元と内容照合、書込主体と削除主体の分離を定めた。365日保持、毎時48時間＋日次30日の世代は**暫定案**であり、実容量と古い値をバックアップが余分に保持する期間を踏まえて決める。バックアップがあることと、復元目標を満たしたことは分けて判定する。

[費用・権限の読み取り確認](storage-cost-permission-check_20261017.md)では、接続済み Google Drive で共有ドライブが見えず、残容量もコネクタから分からないことを確認した。OCI / Google Cloud についても、この利用者環境の実際の書込権限・追加費用は未確認。公開無料枠と合成容量だけで保存先を決めない。

## 実装手順（手動計画レビュー後）

1. Apps の任意の履歴保存機能を既存収集から分離する。既存の `data.json` 公開成功後に履歴の取得・保存を開始する独立経路を設け、Adaptive 30日系列の成否には依存させない。履歴処理の例外・時間切れ・DB ロックは既存公開の成功、収集プロセスの終了コード、Digest の「最終成功」と必須10項目に影響させない。SQLite のスキーマ版、同時実行防止、トランザクション、観測履歴と採用値の2表、再実行時の重複排除、保存失敗の状態記録を実装する。通知は状態変化・継続時間を基準にまとめ、毎時同じ通知を繰り返さない。
2. 公開 Web 領域の外に専用の保存先と最小限のアクセス権を用意し、DB・WAL などの付随ファイルが Web サーバーの設定・リンク経由でも公開されないことを確認する。バックアップは**稼働インスタンスのディスク障害と分離**する。同じ OCI ディスクへのコピーだけでは合格としない。OCI Object Storage を選ぶ場合、同じ OCI アカウントや東京リージョン全体の障害は分離できないことを残余リスクとして判定する。SQLite のバックアップ API を使い、取得時のロック・整合性、世代・保持期間、暗号化の要否、容量監視、別の場所への復旧を試す。復旧目標は「失う履歴を最大1時間程度、復旧を24時間以内」を提案値とし、バックアップ周期・失敗通知・費用の実測と利用者判断で確定する。まず候補の容量・費用・権限を読み取り確認し、合成データの容量帯から保存先を選ぶ。外部保存先への試験転送や権限設定はその操作を承認された後に行う。本番の履歴保存を有効にする**前**に、確定した実装スキーマの合成DBで容量と破損・復元試験をやり直し、選定した外部保存先から別パスへ戻す演習を通す。本番の初回DBの復元確認は保存開始**後**の別ゲートとする。
3. Apps に履歴からの30日系列と比較器を加える。720時間が揃った系列、1440時間が揃った場合の比較結果、可否・理由、出典・精度・時間境界をそれぞれ任意ブロックとして出力する。既存の `trafficSeries30d` と別に検証してから表示全体を切り替える。切替後は旧 Adaptive 30日系列の失敗だけを理由に履歴グラフを無効化せず、国別集計など実際に使う別ブロックの状態は隠さない。現行の収集契約や Digest の必須判定は変更しない。
4. Portal は任意ブロックの版・生成時刻・有効期限、720点・合計の整合を検証する。「未導入」「蓄積中」「比較不能」「保存停止」「取得失敗・形式不正・期限切れ」「比較可能」を区別し、古い系列・比較値を再表示しない。30日グラフの切替前は現行 Adaptive の出典を、切替後は1時間履歴の出典・切替日・確定済み末尾時刻を示す。30日の国別地図には別集計で合計が異なる場合がある旨を示す。24時間は現行取得、7日間は Adaptive という期間ごとの違いを説明する。蓄積中は開始日を示し、「欠測があると、切替までの日数が延びる場合があります」と伝えるが、比較開始日は約束しない。UTC 境界を日本時間で表示し、推計の注記を分かる言葉で示す。
5. Apps の保存、履歴系列・比較結果の出力、Portal の30日グラフ切替、Portal の比較表示を別々のフラグで止められるようにする。保存開始後、**非公開の影の期間**に同期間の履歴・現行1時間・Adaptive の差と欠測を集計する。次に非表示の履歴系列・比較出力、720時間到達後のグラフ切替、1440時間到達後の比較表示の順で有効化する。各段階で定期運転とデータ品質を観測し、次へ進む条件を別々に判定する。スキーマ移行は前進方向で行い、旧コードが新 DB を読めない場合は旧コードを履歴 DB へ接続しない。

## 検証と受入条件

- 時刻を差し替えられる構造と約73時間の遡及上限を模した疑似応答で、720時間未満・ちょうど720時間・1440時間未満・ちょうど1440時間、末尾の仮値、境界が1時間ずれた窓、前期間だけ欠測、途中欠測、正当な0件、重複、再実行、二重起動、遅延更新、凍結後の改訂、抽出率の変化、部分応答、API 保持期限超過、DB ロック・容量不足・途中失敗、破損と復旧を検証する。1440時間あっても出典・契約・精度が異なる場合は比較を出さないことも確認する。
- 1年間の時間別履歴について、最初・最後の時間境界、年をまたぐ時期、古い記録の削除、再実行時の容量増加、改訂履歴の上限を検証する。容量は小さいと決めつけず、採用値、改訂履歴、索引、WAL、バックアップ世代から実容量を見積もる。将来のグラフが時間別値とその推計状態を取り出せる契約にする。
- Apps と Portal の契約テストで、任意ブロックの欠落・不正・期限切れ、保存例外、時間切れが、既存の `data.json` 公開、終了コード、Digest 判定、24時間・7日間・各期間の国別表示に波及しないことを個別に確認する。30日グラフを途中から別出典で継ぎ足さず、30日国別表示との出典差を明記することも確認する。
- 本番では初回取り込み、次回以降の定期書き込み、独立先へのバックアップ、整合性検査、別パスへの復旧を別々に確認する。復旧した DB の期間境界・件数・採用値の一致を確かめる。30日グラフは720時間、比較は1440時間が実際に揃ってから受け入れる。認証済み PC / スマートフォンで表示と比較不能時の文言を確認する。

## 未決定事項とレビューゲート

データセットは `httpRequests1hGroups`、公開用の30日・60日窓の許容欠測は0時間に決定。時間差の実測から採用・凍結・改訂上限、重ね取りと通知の期限、抽出行の比較基準を決めてから保存実装へ進む。保存先・独立バックアップの実在と権限、周期、復旧目標、容量、運用担当を確定し、別パスへの復旧が通ってから本番保存を有効にする。実装前の設計を上記の実測に合わせて再確認する。新しい有料サービスや権限拡大が必要なら別途判断を受ける。

## 戻し方

比較表示に誤りがあれば Portal の比較表示フラグを止める。履歴グラフに誤りがあれば Portal の30日切替フラグを止め、現行 Adaptive グラフへ戻したことを出典表示で確認する。計算だけの異常なら Apps の履歴系列・比較出力を止める。保存で障害や想定外の費用が出た場合は Apps の保存フラグを止め、既存収集・Digest の経路を維持する。スキーマ移行後に旧コードへ戻す際は、旧コードから履歴 DB を切り離し、DB 自体は削除しない。DB を失った場合は独立バックアップを別パスに復旧し、整合性と期間を照合してから再接続する。保存済みデータは調査・バックアップ方針に従って扱い、無断で消去しない。
