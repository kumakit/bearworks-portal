# Issue #403 手動計画レビュー依頼（改訂案）

2026-10-17 に受領済み。指摘の採否は[再レビュー対応記録](../../history/20261017_issue%23403_plan_rereview.md)を参照。以下は依頼時の文面として残す。

対象: [実装計画案](implementation_plan.md)
正本: https://github.com/kumakit/mission-control/issues/403

初回レビューの採否は[対応記録](../../history/20261017_issue%23403_plan_review.md)にまとめた。利用者は、1年間保存する履歴に短期の1時間集計を選び、30日グラフも履歴が揃ってから同じ出典へ切り替える方針を選んだ。この改訂案の手動レビューを依頼する。

追加実測では、現行30日照会が毎時収集直後に一部取得となり、数分後の同期間再照会では検証を通った。また、同じ24時間でも短期の1時間集計と現行30日用の推計集計は23/24時間で値が異なった。再レビューでは、1時間履歴の採用・凍結規則、短い API 保持期間内での欠測回復、30日グラフと比較の段階的切替を重点確認する。

選択した1時間集計についても、公開済みの24時間ブロックと同じ期間を約16分後に再照会すると、直近1時間だけ値が変わった。値が安定するまでの時間はまだ測れていない。

**読み取り専用**でお願いします。実装、ファイル変更、Git操作、Issue/PR更新、API照会、本番操作はしないでください。認証情報、ゾーン識別子、本番の生データ、private資料は渡しません。

確認してほしい点:

1. 約3日の `httpRequests1hGroups` 遡及上限で、失敗・遅延・後から変わる値を回収できる設計か。欠測をゼロで埋めず、期限を越えた場合の扱いが明確か。
2. 1年間の時間別履歴を残しながら、同じ時間の重複・遅延更新・抽出情報の変化をどう扱うか。採用・凍結規則と改訂履歴の上限を決めるための実測は十分か。
3. 720時間後の30日グラフ切替、1440時間後の前期間比の条件に抜けがないか。旧 Adaptive 値と1時間履歴を混ぜていないか。国別表示は Adaptive のままなので、出典と合計の差が利用者に伝わるか。
4. 保存失敗や比較不能が既存の24時間・7日間・国別地図・Digest 必須10項目に波及しないか。
5. 公開領域の外に SQLite を置く案、1年保持、バックアップ・復旧・容量監視を決める前に必要な確認は十分か。
6. テスト、段階公開、戻し方と、履歴が揃う前の画面文言が妥当か。

各指摘に重要度、理由、計画の変更先を付け、確認済みの事実・推測・未確認事項を分けてください。特に、現時点で決められない設計判断は必要な証拠を挙げてください。
