# Issue #403 保存先の比較と仮容量測定

確認日: 2026-10-17 JST。これは設計用の比較であり、保存先の選定・作成や本番データの転送は行っていない。下記の容量測定は**合成データ**だけを使用する。

## 役割を分ける

- **稼働中の履歴DB**: 1時間ごとの追加、遅延更新、重複排除、採用値の照会を行う。現行計画の第一候補は OCI インスタンスの公開領域外の SQLite。
- **独立バックアップ**: インスタンスやディスクが失われた際に履歴DBを戻す。稼働DBとは別の障害領域に時刻別の整合したファイルを保存し、取得・復元を演習する。

| 候補 | 稼働DB | 独立バックアップ | 判断に必要な確認 |
| --- | --- | --- | --- |
| OCI Object Storage | ファイル保管なので稼働DBとしては使わない | OCI Compute とは別サービス。ただし同じ OCI アカウント・東京地域の障害は分離しない | バケット作成、インスタンス権限、区分と無料枠、保持・削除、復元 |
| Google Drive | ファイルAPIで行単位の更新・照会を提供せず、稼働DBには不向き | 時刻別 SQLite バックアップの置き場所になり得る | 共有容量の残り、ユーザー OAuth の更新・失効、ファイルの共有範囲、復元 |
| Google Cloud Storage | ファイル保管なので稼働DBとしては使わない | OCI とは別事業者。オブジェクト保存と権限管理に向く | Google Cloud の課金設定、保存地域、容量・操作・転送費、権限、復元 |
| 別端末から定期取得 | 端末側を正本にする案ではない | OCI とは別の端末・場所に退避できる | 端末稼働、取得失敗の通知、保管期間、復旧担当、復元 |
| BigQuery | 時間別行の保存・SQL集計は可能。ただし追加の権限・重複排除・改訂・課金設計が必要 | SQLite ファイルをそのまま戻す方式にはならず、行からの再構築が必要 | 分析需要、課金設定、1年保持、取得と再構築。現段階では採用しない |

[Oracle の無料枠](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)はアカウント区分によって説明が異なり、利用者の Console では区分を明示確認できなかった。[Google の個人アカウントの最大15 GB](https://support.google.com/drive/answer/9312312)は Gmail・写真と共用。[Drive サービスアカウント](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)は自身の保存容量とファイル所有権を持たない。[Google Cloud Storage の無料枠](https://cloud.google.com/storage/pricing)の月5 GBは米国の指定地域のみ。[BigQuery Sandbox](https://docs.cloud.google.com/bigquery/docs/sandbox)では表などが60日で失効するため1年保持には使えない。これらは各サービスの公開条件であり、利用者のアカウントの残量・権限・実費の証拠ではない。

## 合成データによる SQLite サイズ測定

[測定スクリプト](estimate_history_storage.py)で、仮の採用値表・観測表・索引を作り、365日分（8,760時間）の合成値を挿入した。SQLite のバックアップ API で別ファイルへ複製し、`integrity_check` と行数を確認した。測定ファイルは Git 対象外の `.local-research/issue-403/` にだけ置いた。**本番の集計値、認証情報、ゾーン識別子は使っていない。**

| 1時間あたり保存する観測行 | 年間の観測行 | DB本体 = 整合したバックアップ1世代 | 書込中のWAL最大観測値 |
| ---: | ---: | ---: | ---: |
| 1行 | 8,760 | 約0.81 MB | 約0.84 MB |
| 4行 | 35,040 | 約2.34 MB | 約2.38 MB |
| 72行 | 630,720 | 約39.00 MB | 約39.26 MB |

72行は「重ね取りした値をすべて新規行として保存する」過大な例であり、採用設計では同じ観測の重複排除と改訂上限を設ける。測定値は仮スキーマ・合成値・単一DBに限る。実際のメタデータ、索引、トランザクション、空き領域、バックアップ世代、その他のサービス利用を含まない。**バックアップ先が無料枠内で運用できるという証明にはならない。**

次に、時間差観測を踏まえて重複排除キー・改訂上限・365日か暦年かの保持定義を決める。実装スキーマで1年分を再測定し、バックアップ1世代の実サイズ×保持世代数に余裕を加えて各候補の残容量・費用を照合する。バックアップ世代に削除済みの古い時間が残る期間も、保持方針として明示する。
