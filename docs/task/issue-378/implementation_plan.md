### 2. データ可用性を調査

成果物: `data-availability.md`。地点×要素×期間について以下を記録する。

- 地点番号とETRN block_no、所在地・移設、観測種別。
- 気温、降水量、相対湿度、気圧、降雪量、積雪深、天気・降水形態それぞれの提供有無、開始・終了、時間粒度、品質・欠測表現。
- CSV/HTML/公的報告の取得手段、取得制限、利用条件、出典URL、確認日。
- 推計気象分布等は利用可能期間・解像度・入手条件を確認し、直接観測とは別の候補にする。
- 八王子と東京都心を必須、府中・青梅を補助候補とする。代替地点は距離だけで選ばず、観測項目と地形・標高差も明示する。
- 項目の開始時点付近、過去年代、直近冬、候補イベントから少量の実データを確認する。ページに列があるだけで観測可能とは判定しない。

今回の予備確認では、気象庁の2026-03-24現在の観測所一覧に八王子・府中の湿度除外注記はなく、積雪観測所番号の併記はない。これは現在の設備情報であり、過去の湿度提供開始年月や降雪観測の全履歴を確定するものではない。時別ページの本文取得は失敗しており、実データの取得可否・期間は未確認。

取得は公式に案内されるCSVを優先し、HTMLは公式提供表の補助確認に使う。非公開・非公式APIを前提にしない。rawを上書きせず取得条件・SHA-256を保存する。時別CSVの分割が必要なら、重複期間とsnapshotごとの均質番号の照合方法を先に定める。

ゲート: 各仮説に必要な項目の可否と比較可能期間が根拠付きで説明できること。直接検証できない仮説は理由と代替案をこの段階で記録する。

### 3. 分析設計を固定

成果物: `analysis-design.md`。本取得・仮説の結果集計前に、対象期間、判定基準、分母、除外条件、イベント選定を固定する。

| 仮説 | 主な評価 | 制約時の扱い |
|---|---|---|
| H1 降水時に八王子が低温 | 同時刻の気温差、中央値、八王子が低温の割合、冬別・イベント別のばらつき | 気温・降水が共に利用可能な期間だけ比較 |
| H2 都心雨でも八王子は雪条件 | 都心の観測された雨と八王子の気温・湿度による条件指標を照合 | 湿度がなければ湿球温度を作らない。都心の雨が観測できなければ「都心は雨」と表示しない |
| H3 南岸低気圧で差が明瞭 | 公式資料で同定したイベントと、同季節・時間帯などを揃えた非イベント降水時を比較 | 気温差と降水形態を別々に判定。事例しか取れなければケーススタディに限定 |
| H4 早い雪条件入り・大きな積雪影響 | 条件入り時刻差、直接観測された降雪開始、公的な積雪・影響記録を別指標にする | 時間粒度より細かい先行は主張しない。積雪影響は気温・降水量から作らない |

設計上の既定方針:

- 時別値、JST、同時刻ペアを基本とする。冬は12〜2月の完結季節。候補は既存記事と整合する1990〜2025年だが、利用可能性に応じて気温比較と湿度比較の期間を分ける。
- 「降水時」は両地点の降水観測が有効かつ少なくとも一方で1時間0.5mm以上を初期案とする。両地点で降水がある場合だけの感度確認も行う。採否は可用性調査後・結果を見る前に固定する。
- `ΔT = 八王子 - 東京都心` と定義し、負値が八王子の低温を示す。時間数だけでなく独立したイベント数も示し、連続した時刻を独立標本扱いしない。
- H1の「多い」、H2の「多い」、H3の「明瞭」を定量化する閾値と不確かさの評価法、最低イベント数は調査後に事前固定する。結果に合わせて閾値を変更しない。
- 湿球温度を採用する場合は、計算式の一次資料、必要な入力、氷点下を含む適用範囲、誤差、閾値感度を確認する。地上条件の指標から実際の降雪を断定しない。
- 湿度不可用時は低温頻度・気温分布へ切り替える。気温0℃・2℃等の区切りを雨雪判定として使わず、H2等の直接検証不能を維持する。他地点の湿度で補完しない。
- CIはイベント集合の平均差に付け、個々のイベント差の散らばりと別表示する。相関の説明には日周・季節・気圧配置など共通要因の可能性を含め、原因が実証されたとは扱わない。
- 南岸低気圧は公式資料・天気図から選び、雪が多い事例だけを抽出しない。主要降雪事例を複数含め、非降雪事例も比較候補にする。
- 有効率は項目の観測可能期間に対して計算し、同時刻ペアの成立率と降水判定が欠測で不明な時間も報告する。旧記事の日別90%基準を時別へ無条件に流用しない。
- 欠測、非観測、対象外、資料不足、実測0、微量等の原記号と品質情報を保持する。非数値は `null` と理由を持ち、`0`へ変換しない。
- 結果と公開上の強さを分離し、資料不足・直接検証不能を不支持や0件に置き換えない。

ゲート: H1〜H4ごとに実施可能な検証、できない主張、代替案を説明できること。要求する結論や対象範囲が変わる場合に限り、判断材料を提示して確認する。

### 5. 可視化・記事実装

Portal側の候補:

- `app/(monetized)/labs/hachioji-snow/page.tsx` と `data/`。
- `lib/hachioji-snow-publication.ts` と `scripts/validate-hachioji-snow-bundle.mjs`。
- `app/site-content.ts`、ホーム・既存記事からの導線、`lib/content-provenance.ts`。
- `package.json` の検証コマンドと `.github/workflows/workers-build.yml` の必要なroute検証。

記事は導入、問い、雪の測り方、冬の気象条件、雨雪境界、複数事例、結論、限界を扱う。先にデータ可用性表・降水時気温分布・イベント時系列を作る。湿球温度散布図やケース一覧は根拠がある場合だけ追加する。

追加要望により、各分析を「身近な問い → 図 → 読み取れること → 統計検定2級の手法 → ミニ設問・演習」の順で構成する。記述統計、対応のある差の推定・検定、相関・単回帰、条件付き割合を主要候補とし、前提を満たさない推測統計は実データの結論に使わない。時系列図・ヒストグラム・箱ひげ図・散布図の4種を基本に、適用可能なら信頼区間図を追加する。

`app/(monetized)/toukei/page.tsx`、関連guideの既存構造に合わせ、学習サイトから「実データで学ぶ」導線を追加する。記事からは手法別guide・problem・ドリルへ戻せるようにする。UIの詳細と画像制作方針は `content-design.md` に固定する。

既存のヘッダー、フッター、カード、配色、ContentProvenance、InternalLinkを再利用する。グラフはHTML表と本文でも読めるようにし、観測と推計は凡例と注記で区別する。bundleの内部フィールド名を本文の説明代わりにしない。

- データ: 欠測/非観測/0/微量のfixture、時刻・季節境界、同時刻ペア、利用不能項目、均質区間、閾値境界、仮説の資料不足判定をテストする。
- 再現性: 同じ入力の再生成一致、bundle/lock/hash整合、改変時の検証失敗、本文・表・図の主要値の一致。
- 既存記事: 東京の正式データ名とbundle hashが維持され、読者向け表示と定義注記が揃う。
- Portal: `npm run lint`、型検査、既存/雪bundle検証、`npm run build`、`npm run cf:build`、`git diff --check`。
- Apps: 既存実行環境に合わせた関連テストと雪分析テスト、既存気候分析の回帰確認。
- ブラウザ: PC/モバイル、グラフ軸・凡例・表の横スクロール、キーボード操作、欠測が0として描画されないこと。
- 学習体験: 手法名、標本単位、主要式、解釈、ミニ設問、対応guideへの導線を確認する。p値・信頼区間・条件付き確率の誤解を生む表現をレビューする。

- 視覚表現: 導入画像と独自説明図、4種以上の基本グラフ、データが許す場合の区間推定図を確認する。写真の出典・撮影情報、説明図/生成イラストの区別、alt、画像容量・表示の安定性も確認する。
