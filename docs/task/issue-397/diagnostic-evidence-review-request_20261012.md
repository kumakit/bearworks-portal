# Issue #397 定期収集の診断証跡 手動計画レビュー依頼

対象: [Issue #397](https://github.com/kumakit/mission-control/issues/397)、[詳しい計画](./diagnostic-evidence-plan_20261012.md)。

## 何をしたいのか

ダッシュボードは1時間ごとに新しいアクセス情報を取りに行きます。10月12日は、30日間の情報を一部取れない回がありました。後の回で結果が上書きされたため、別の回で何が取れなかったかは分からなくなっています。

そこで、各回について「いつ、どの項目が、取れたか／取れなかったか」と理由の種類だけを運用ログに残します。アクセス件数、国別の内訳、IPアドレス、認証情報は残しません。グラフの数値や、取れない情報を画面に出さない現在の判断方法も変えません。この方法で、次に同じ問題が起きたとき原因を追えるかをレビューしてください。

## 確認してほしい点

1. 収集と、その結果を使う定期報告について、**どの回のどの項目が失敗したか**を後から結び付けられるか。計画では、収集ごとの識別番号（`runId`）と時刻を使います。
2. 記録するのは**項目名・取得状態・失敗理由の種類だけ**で十分か。アクセス件数、国別の内訳、IPアドレス、Cloudflareの対象識別子、APIからの返答全文、例外の文章、秘密情報が紛れ込まないか。
3. **取れなかった、古くなった、設定で止めた**を正しく区別できるか。現在の「使えるデータか」を調べる処理（`usable_data()`）と同じ基準を使い、画面や定期報告の判定を変えないか。
4. 1時間ごとに短い記録を増やしても、既存のログ保存・古いログの整理（ローテーション）と実行時間に問題がないか。別の保存場所が必要か。
5. 失敗時のテスト、変更したファイルだけの本番反映、元に戻す手順は十分か。今回の変更はまず**失敗理由の記録に限定**し、推計値の食い違いに対する再実行や合格条件の緩和は、記録が集まるまで待つ判断でよいか。

## 用語

- **Digest**: 収集結果を使って定期的に作る運用状況の要約。
- **`partial`**: 必要な情報の一部を使えない状態。サイトの危険や停止を意味する言葉ではありません。
- **`runId`**: 1回の収集につける識別番号。収集とDigestの記録を対応させます。
- **エラーコード**: 失敗理由を表す短い分類名。APIの返答全文や秘密値ではありません。
- **Adaptiveの推計値と母数**: Cloudflareが一部を使って推定した件数と、割合などを計算するときの全体件数。
- **ロールバック**: 問題が出た場合に変更前のコードへ戻すこと。

指摘ごとに「採用／条件付き／不採用」、根拠、計画変更箇所を示してください。確認済みの事実と推測を分け、実装・GitHub更新・本番操作は行わないでください。秘密値、個別のアクセス情報、非公開ファイルの内容はレビューへ渡さないでください。
