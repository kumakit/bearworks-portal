# Issue #397 Phase 3B: セキュリティイベント推移の採用判断

作成日: 2026-10-15 JST
正本: https://github.com/kumakit/mission-control/issues/397

## 目的

アクセス推移とは別に、Cloudflare が返す Firewall イベントの時間別件数を参考情報として表示できるか判断する。攻撃件数、危険度、遮断率、安全性の判定には使わない。履歴保存と30日アクセス前期間比は、利用者の指定どおり別フェーズに残す。

## 2026-10-15 の読み取り調査

本番収集と同じ Free ゾーン・既存の読み取り資格情報で、設定と件数のみを照会した。資格情報、ゾーン識別子、個別イベントは記録していない。

| 確認項目 | 実測結果 | 解釈 |
| --- | --- | --- |
| `firewallEventsAdaptiveByTimeGroups` | `enabled=true`、最大照会30日、遡及31日、最大10,000行 | 現環境では候補データセットを利用できる |
| 実スキーマの説明 | 「抽出を含む Firewall イベントの時間別集計」と明記 | 「Firewall イベント」という表示の根拠になる。イベント詳細や危険度までは示さない |
| 完了した直近24時間 | 時間別7行、GraphQLエラーなし、`sampleInterval` は全行1 | 空白の時間は返らない。未返却時間をゼロと確定してはいけない |
| 完了した直近7日 | 時間別67行、うち3行で `sampleInterval>1` | 一部の件数は抽出データからの推計 |
| 完了した直近30日 | 時間別97行、全行で `sampleInterval>1`、最大値110は `sampleInterval` | 30日の値を全件実数として表示できない |
| 処理種別 `action` | `settings.availableFields` には候補があるが、`dimensions { action }` の実照会は GraphQL エラー | 現段階では遮断・許可などの内訳を表示しない |

実スキーマと公開された [Cloudflare のデータセット説明](https://developers.cloudflare.com/analytics/graphql-api/features/data-sets/)から、時間別の Firewall イベント集計であることを確認した。[Security Events の説明](https://developers.cloudflare.com/waf/analytics/security-events/)では生イベント `firewallEventsAdaptive` が基礎データとされるが、`ByTimeGroups` と完全に同じ範囲か、空白時間がゼロか取得遅延かは今回の照会だけでは確定しない。[抽出集計の説明](https://developers.cloudflare.com/analytics/graphql-api/sampling/)に従い、`count` は毎回の `sampleInterval` を見て推計の可能性を表示する。24時間の今回の値が非抽出だったことは、次回以降の保証ではない。

同日22:00 JST の収集診断は必須10項目すべて利用可能。22:20 JST の Digest はその収集と実行番号が一致し、`cfAvailable=true`、利用不可0、公開状態 `ok`・期限内・エラー0件だった。これは当該定期実行1回の証跡であり、継続安定の証明ではない。

## 採用条件と設計

1. **名称と説明**: 表示名は「Firewall イベントの記録数（参考）」とする。注記は「Cloudflare が抽出を含めて集計した時間別の記録です。攻撃・遮断・安全性の判定ではありません」。単位は API が返したイベントの `count` とし、HTTP リクエスト数や訪問人数とも同一視しない。既存の `traffic24h.threatEvents` や旧「WAF時系列」と並べず、足さず、比率にも使わない。
2. **時刻と欠け**: 現在のアクセス推移と同じ UTC 正時で区切り、各期間を開始時刻を含み終了時刻を含まない `[windowStart, windowEnd)` として24時間・7日・30日を独立照会する。返った時間の値だけを点で示し、点の間を線で結ばない。返らない時間は空白と「未確認」で示し、0件・「記録なし」とは書かない。欄には「値を取得できた時間 N / 24・168・720」を示す。直近の空白には集計反映前の可能性も注記する。新系列は疎な点を許す独立の検証規則を使い、既存アクセス系列の連続点検証を流用しない。`windowEnd` は直前に完了した UTC 正時、`attemptedAt` は原則その後1時間以内とし、遅れた実行はそのブロックだけ利用不可にする。個々の時間の欠けを理由に期間全体を失敗にしない。
3. **値と精度**: Cloudflare の説明では抽出時の API 集計値はすでに推計なので、グラフには返却された `count` を使い、`count × sampleInterval` はしない。各時間の `sampleInterval` は精度判定の情報として保持する。1を超える点とその期間に「推計を含む」を表示する。30日は現実測で全点に必要。期間合計を出さず、精度の異なる期間を直接比較しない。返却された0は「この集計の返却値0」と扱い、実イベントが皆無だったとは断定しない。負数・非整数、間隔が有限の正数でない場合は、そのブロックを利用不可にする。
4. **独立した契約**: 既存 schema v2 に任意のセキュリティ系列ブロックを追加する。Portal は `SECURITY_KEYS` と独立した解析・評価関数を設け、既存 `ACCESS_KEYS`、`monitoredKeys`、全体の `counts`・状態・対応操作、`CloudflareCollectionView` の `accessKeys` と「データについて」のアクセス項目には入れない。Apps 側も既存 `ACCESS_NAMES` と Digest の `required_cloudflare_names` に入れない。欠落した新ブロックは「未収集」、不正・失敗・期限切れはその欄だけ「未確認」または「利用不可」とし、正常な0へ変えない。既存のアクセス8項目、Pages、Digest の必須10項目は変えない。
5. **表示**: 主画面の末尾に初期状態を閉じた独立の参考欄を置く。開くと返却された時間の点と値、抽出の注記、欠けの説明を見られるようにする。色だけに頼らず、文字・形でも点の状態を伝える。利用不可または期限切れの期間は参考欄だけに理由を示し、選択中の期間を勝手に変えない。キーボードとスマートフォンでも読めるようにする。

## 実装前に解消する点

- **A 合格条件**: 画面の名称・注記を上記の確認済みの範囲にとどめ、`threatEvents`、アクセス件数、攻撃・遮断件数との同一視がない。生イベントとの詳細な対応が確認できなければ、それ以上の説明や比率を追加しない。
- **B 合格条件**: 疎な返却を0補完せず、点のない時間を空白・未確認と示し、取得できた時間数と直近の反映遅延の可能性が分かる。遅れた収集は参考欄だけ利用不可となる。0件と断定するには別の根拠が必要。
- **C 合格条件**: 新系列だけが欠落・失敗・期限切れ・不正でも、Portal のアクセス表示・全体の `counts`・状態・対応操作、Apps の診断ログの必須項目・`unavailable`・`cfAvailable`、Digest 必須10項目・公開状態が変わらない。Apps 本番の現行 `flatten` と Digest 必須集合は固定キーだけを使うことを読み取り確認済みだが、追加後もテストで固定する。
- **D 合格条件**: `count` を再乗算せず、API 値そのものを点として表示する。抽出がある点・期間は推計と明記し、合計・期間間比較を出さない。[Cloudflare の抽出集計説明](https://developers.cloudflare.com/analytics/graphql-api/sampling/)を根拠とする。
- **E 合格条件**: 時刻は範囲内の正時に限る。`sampleInterval` は `avg` フィールドであり集計の次元ではないため、同じ時刻が複数行返ったら間隔の異同にかかわらず安全に合算せず、そのブロックを利用不可にする。上限10,000行到達、GraphQL の部分エラー、範囲外の時刻もそのブロックを利用不可にする。抽出率の大きな変動は点ごとの推計表示に反映する。

## 確認と反映の順番

1. A〜E の合格条件を、コードと表示文言に落とせることを確認して採用可否を決める。採用不可でも現行アクセス画面は完成扱いを保つ。
2. 採用時のみ Portal の任意ブロック読み取りと独立した参考欄、Apps の収集契約を実装する。検証は24時間・7日・30日の先頭・末尾と範囲外の正時、正時直前・直後・遅延実行、0・1・疎・全時間の行、上限到達、部分応答（データあり・なし）、同時刻の重複（間隔同一・相違）、間隔1と1超の混在・全点1超、0・負・非整数の件数、新ブロック欠落・不正・失敗・期限切れを含める。30日の開始は31日遡及限度内に収める。旧 WAF 5 項目を復活させない。
3. ローカル画面と独立レビュー、PR/CI を確認する。Portal の読み取り側を先に配備し、Apps を機能フラグ無効のまま配備してから有効化する。その後の定期収集・Digest、認証済み画面を確認する。新キーを含む schema v2 を旧 Portal と現行 Apps が無視できること、新キー欠落を未収集とすることをテストする。各外部書き込みは承認範囲を確認する。
4. 表示が誤解を招く、アクセスの値を壊す、欠測・推計を隠す場合はセキュリティ参考欄を無効化または当該変更だけ戻す。既存のアクセス表示と Digest は維持する。
