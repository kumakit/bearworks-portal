# Issue #403 手動計画レビューへの対応

2026-10-17 JST。受領したレビューは計画書だけを読んだ結果であり、Issue #397 の実測や Apps の現行コードをレビュー担当者が再確認したものではない。以下は Codex が現行コードと既存の実測を照合した採否。参照元: [改訂計画](../task/issue-403/implementation_plan.md)、[Phase 2 実測](../task/issue-397/phase2-evidence-status_20261012.md)。

| 指摘 | 判断 | 計画への反映 |
| --- | --- | --- |
| 1. 前期間と現在期間の値が固まる時期 | 一部採用 | 両方の30日窓を「終了から同じ経過時間」で取得する条件を追加した。どちらも終了直後に取得すれば取得時点の遅れ方は対称なので、非対称と断定はしない。値の後日変動は未測定で、実測後に待ち時間を決める。 |
| 2. 時間別値の採用規則 | 採用 | 観測の変更を追跡し、採用・凍結・改訂上限を実測後に確定する。決まるまで履歴保存の実装へ進まない。 |
| 3. 独立したバックアップ | 採用 | 稼働 DB と別の障害領域、整合性検査、別パスへの復旧を本番保存の条件にした。候補と費用は未確認。 |
| 4. 抽出条件の記録 | 採用 | 現行 API 照会は各行と全体値の `sampleInterval` を返す。分布を保存し、許容範囲は実測で決める。 |
| 5. 時刻の厳密一致と欠測 | 一部採用 | 期間がずれた値や古い比較を代用しない。該当する比較だけ理由を示して利用不可とする。日次窓への変更は現行の時間別30日表示と期間がずれるため、今回は採用しない。 |
| 6. 保存失敗の隔離 | 採用 | 既存の収集・検証後に、時間・ロック待ちを制限した任意保存を試みる。失敗しても既存の公開を続け、同じ失敗の通知をまとめる。 |
| 7. Portal の状態区分 | 採用 | 未導入、蓄積中、比較不能、保存停止、取得失敗・形式不正・期限切れ、比較可能を分け、古い値を出さない。 |
| 8. 3段階の停止とスキーマ | 採用 | 保存・比較出力・画面表示の独立フラグ、段階公開、旧コードから DB を切り離す戻し方を追加した。 |
| 9. 容量見積り | 採用 | 空き容量だけで判断せず、行数・行サイズ・変更回数と SQLite の付随ファイルから見積もる。 |

現行 Apps は30日窓に対して時間別・国別・全体を同じ条件で独立照会し、時間別の和と全体値を照合する。過去の実測では720時間と全体値が一致したが、これは将来の一致や推計精度の保証ではない。[追加の読み取り確認](../task/issue-403/phase0-additional-evidence_20261017.md)では直後の再照会5組が一致した一方、後日の変動と独立したバックアップ先は未確認。実装着手の判定は保留する。

追加実測で、公開後約1時間の再照会では期間末尾の1時間だけ値が変化した。また、次の毎時収集直後は30日窓の時間別和と全体値が一致せず、数分後には一致した。指摘1の「値が固まる時期」を実測で扱う必要性が強まったが、原因は遅延更新と Adaptive の抽出をまだ分離できない。短期1時間集計と Adaptive 集計の値も多くの時間で異なり、データセット選択を再レビューの必須項目に加えた。

その後、利用者は `httpRequests1hGroups` の1年履歴を選び、30日グラフも同じ出典の履歴が揃ったら切り替えると決めた。上表の「30日窓を同じ経過時間で取得する」案は旧 Adaptive 保存案に対する当時の回答であり、改訂計画の比較方式には使わない。改訂計画では、連続した720時間でグラフ、1440時間で前期間比を判定する。短期集計の採用・凍結規則と独立バックアップは引き続き未決定で、手動再レビューが必要。
