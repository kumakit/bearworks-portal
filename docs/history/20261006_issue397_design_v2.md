## 3. 現行実装で確認した問題

1. 収集側の`fetch_cloudflare_metrics()`は取得失敗を捕捉した後も、初期値の0や途中までの集計値を返す。値だけでは成功と失敗を区別できない。
2. WAF詳細ではGraphQLの部分エラーを許容し、欠けた項目を空配列などに変換する。項目単位の取得状態が出力されない。
3. Pagesプロジェクト一覧の取得失敗は0件になり、デプロイ一覧の途中失敗では一部だけの件数が返る。固定の500回を上限として使用している。
4. 必須設定が不足すると収集側がモック全体を生成する経路がある。現行の出力型には、実データかモックかを示す情報がない。
5. portalはAPI失敗時にモックを表示する。API自体が成功した場合でも、WAF詳細欠損をモックで、Pages欠損を0で補完する経路がある。
6. portalは脅威数100件を境に「平常」「脅威検出増加」を表示するが、その運用上の根拠は未確認。
7. アクセス統計は24時間、WAF詳細は7日間。ゾーン単位のアクセス統計と、アカウント内のPages集計は対象範囲も異なる。

## 4. 対象範囲と非目標

### 対象

- 収集結果の由来、成功・失敗、対象期間、取得範囲を明示する追加データ。
- Cloudflare画面での取得状態の検証と、欠損・古いデータ・モックの表示。
- 根拠付きの総合状態、理由、推奨アクション、各指標の説明。
- 判定の単体テスト、収集失敗のテスト、新旧形式の組合せ検証、画面検証。
- AI Operations Digestが無効なCloudflare値を正常値として利用しないための最小限の対応を、F8の採用案として追加する。対象は取得・状態伝達・入力制限・テストであり、新しいLLM機能は追加しない。

### 非目標

- WAFルール、Cloudflare Access、DNS、認証情報、API権限の変更。
- サイトの無侵害・無停止の保証、攻撃者や攻撃成功の断定。
- AIによる都度の危険度判定、学習型の異常検知、通知サービスの新設。
- Workers利用枠や新しい監視データの収集を、Pages表示の修正に紛れて追加すること。
- GCP課金計算や他画面の全面改修。
- 初期版での前期間比・連続失敗判定のための履歴保存。必要性が確認された場合は別途計画範囲を判断する。

## 6. 追加するデータ契約

以下はレビュー対象の名称案。既存の数値項目は互換用として当初は削除・型変更せず、トップレベルへ`cloudflareCollection`を追加する。新portalとAI Digestは、Cloudflareの判定・表示用数値をこの新オブジェクト内の`data`からのみ取得し、旧数値へフォールバックしない。

### 対象ブロック

- `traffic24h`: リクエスト・脅威・キャッシュの24時間統計。
- `waf7d.summary`: 7日間の処理種別別集計。
- `waf7d.topRules`、`topPaths`、`topASNs`、`timeline`: 詳細項目ごとの取得状態。
- `pagesMonth`: Pagesの当月集計。

### 共通項目

| 項目案 | 値・意味 |
| --- | --- |
| `schemaVersion` | 追加オブジェクトの版。初期値1。未対応の版は判定に使わない |
| `runId` | 実行ごとに生成する識別子。ルートと各ブロックで一致必須。秘密値ではない |
| `data` | ブロックに対応した今回の数値・配列。失敗・不明はnull。以前の値を繰り越さない |
| `source` | `LIVE` / `MOCK` / `UNKNOWN` |
| `status` | `OK` / `PARTIAL` / `ERROR` / `UNKNOWN` / `DEMO` |
| `attemptedAt` | 今回の取得を試みた時刻。未実行ならnull |
| `collectedAt` | 今回、有効なデータを取得した時刻。失敗ならnull。全体のupdatedAtで代用しない |
| `windowStart` / `windowEnd` | 数値が表す集計期間。タイムゾーン付き日時 |
| `scope` | ゾーン全体・アカウント全体等の種別と表示名。秘密のIDは追加しない |
| `validUntil` | 有効データを判定に使用できる期限。鮮度ポリシー未設定・失敗時はnull |
| `coverage` | `FULL` / `TOP_N` / `INCOMPLETE` / `POSSIBLY_TRUNCATED` / `UNKNOWN` |
| `sampling` | `ADAPTIVE` / `NONE` / `UNKNOWN`。実際に分からないものを全件実測と記録しない |
| `errorCode` | 閉じた集合: `TIMEOUT` / `ACCESS_DENIED` / `UPSTREAM_ERROR` / `INVALID_RESPONSE` / `MISSING_CONFIG` / `PARTIAL_RESPONSE` / `RESULT_LIMIT` / `UNKNOWN_ERROR`、またはnull |

`schemaVersion`とルート`runId`はオブジェクト全体、それ以外は各ブロックに置く。ブロックは`{ runId, data, source, status, ... }`として値と状態を一体化する。`data`の形は次を基準にする。

- `traffic24h`: `requests`、`threatEvents`、`cachedRequests`、`cacheRate`。母数0の`cacheRate`はnull。他の必要フィールドの欠損は成功にしない。
- `waf7d.summary`: `actionCounts`と`totalEvents`。処理種別が未知なら「その他」として件数を保持し、遮断や正常の根拠にしない。
- `topRules`、`topPaths`、`topASNs`、`timeline`: 対応する配列。成功した空配列と失敗時のnullを区別する。
- `pagesMonth`: 今回確認できた`deploymentCount`。契約上の`buildCount`、`limitBuilds`、`usagePercent`は意味と対象を検証できるまでnull。デプロイ件数をビルド利用枠へ自動変換しない。

### 有効な組合せと同一実行の保証

| source | status | coverage | data・errorCodeの条件 | 利用方法 |
| --- | --- | --- | --- | --- |
| LIVE | OK | FULL | 型・値を検証済み、errorCode=null | 鮮度等の検証後に利用可能 |
| LIVE | OK | TOP_N | 意図した上位一覧だけ、errorCode=null | 上位一覧の事実表示のみ。全体判定へ転用しない |
| LIVE | PARTIAL | INCOMPLETE / POSSIBLY_TRUNCATED | 検証できた今回の部分データ、またはnull。errorCodeはPARTIAL_RESPONSE / RESULT_LIMIT | 参考表示だけ。ブロック全体を必要とする判定とDigestの数値入力には使わない |
| LIVE / UNKNOWN | ERROR | UNKNOWN | data=null。errorCodeは上記の失敗理由のいずれか（PARTIAL_RESPONSE / RESULT_LIMITを除く） | 失敗理由と操作だけ表示 |
| UNKNOWN | UNKNOWN | UNKNOWN | data=null、errorCode=null | 取得状態不明 |
| MOCK | DEMO | FULL / TOP_N | 型を検証したデモ値、errorCode=null、validUntil=null | デモ表示のみ |

表にない組合せ、未知のenum値（errorCodeを含む）、runId不一致は、受信側で当該ブロックを`UNKNOWN`へ正規化する。入力の生文字列は説明へ出さない。契約不正の理由は受信側の固定コードとして別管理する。ルートrunIdがない・壊れている場合は全ブロックを不明とする。

runIdだけでは値の由来の正しさを証明できない。収集関数が今回の値と状態を一つの結果として返し、同じrunIdを付けた全体を一度だけシリアライズする。旧JSONを読み出して値と状態を個別に結合しない。失敗時に前回値を繰り越さないことを契約テストで確認する。

`FULL`は要求した集計範囲について取得が完了したことを表し、サンプリングされていないことを意味しない。上位10項目の取得は意図した`TOP_N`として表示し、全件の合計や安全判定には転用しない。

`sampling=ADAPTIVE`の値は推計であることを明示する。0は「この集計では観測されず（推計）」、`UNKNOWN`の0は「この集計では観測されず（集計方法未確認）」とし、「攻撃0件」「安全」としない。`NONE`でも、表すのは当該集計の0件に限る。将来の閾値・比率ルールは、推計値を扱う条件を明文化するまで有効化しない。nullは観測0と区別する。

### 収集成功の条件

- HTTP状態に加え、JSON構造、GraphQLエラー、必要なフィールドと数値の妥当性を確認する。
- 空の集計結果は、対象ゾーンが存在し、要求が成功し、必要な集計の完全性を確認できた場合に限り0件と扱う。応答構造の欠損を0件へ変換しない。
- 主要WAF集計は補助項目と別リクエストにする。追加リクエスト数と既存制限への影響を実装時に確認する。
- 補助項目の部分エラーは、エラーの対象と有効性を特定できる項目だけ利用する。対応を特定できなければ影響範囲を成功扱いにしない。
- 集計の取得上限へ達したとき、完全性を証明できなければ`PARTIAL`とする。時系列の切り捨てを完全な7日分として表示しない。
- Pagesはプロジェクト一覧と各一覧のページ取得を含めて成功判定する。ページの途中失敗を完全な利用件数としない。
- モック生成経路すべてに`MOCK`を付ける。`--mock`と設定不足によるモックも漏らさない。
- 数値とメタデータが異なる取得回に由来しないようにする。JSON解析失敗時、portalは取得失敗表示にする。
- 既存の直接ファイル書き込みを原子的な置換に変える作業は、今回の必須変更には含めない。読み取り途中の失敗を正常判定へ変換しないことは必須。
- Pagesのプロジェクト一覧が空でも、対象未設定と「確認済みの対象に0件」を区別する。対象・契約が確認できない間、利用枠判定は不明とする。
- 現行コードの月初はUTC。初期版のデプロイ件数は`aggregationTimezone=UTC`を明示し、月初から取得時点までをwindowとして出力する。Cloudflare契約上の月境界との一致は別途確認し、確認前に利用枠残量へ変換しない。

### 鮮度

確認済みの収集間隔と許容する遅れを使って、データの基準時刻から`validUntil`を決める。具体値は本番の実行設定を確認して設定する。設定がない、日時が不正、日時の前後関係が矛盾する場合は判定不能とする。

画面の更新操作やJSON全体のupdatedAtだけで期限を延長しない。期限ちょうどは期限切れ。`windowStart <= windowEnd <= collectedAt <= validUntil`を満たさない成功データは不明とする（日時の許容誤差はU01で設定）。月次のwindowEndも取得時点であり、未来の月末にしない。

APIは認証済みのJSON応答に`responseMeta.servedAt`（UTC）を付ける。これは応答送出直前のサーバー時刻であり、静的な収集JSONから取り出した時刻ではない。既存のAccess判定とno-storeは維持する。エラー応答を取得成功に変換しない。

ブラウザは要求開始・応答受信の単調時計を記録する。サーバー時刻に受信後の経過時間を足し、要求の往復時間を加えた保守的な上限時刻で期限を評価する。端末の壁時計を現在時刻の正本にしない。通信遅延・基準時刻の不確かさが設定上限を超える、サーバー時刻がない、再同期時に許容外の矛盾がある場合は判定不能にする。

バックグラウンド復帰、pageshow、スリープ等で時刻基準を信頼できない場合は再取得まで判定不能にする。定期再同期の間隔と許容誤差もU01の設定対象とし、未設定時は正常扱いにしない。フェイクタイマーで開きっぱなし・遅延・再開を検証する。AI Digestは実行ホストのUTC時刻で同じ期限条件を評価し、本番時刻同期も反映前に確認する。

## 7. 判定と説明の仕様

### 7.1 データ品質と運用状態を分ける

取得成功は監視対象の安全を証明しない。最上部を「データ状態」と「セキュリティ・トラフィックの兆候」の2軸に分ける。各チェックには`domain=COLLECTION`、`SIGNALS`、`FACT`のいずれかを必須とし、結果・理由・使用指標・期間・操作を保持する。COLLECTIONの成功とFACTの事実表示はSIGNALSの正常件数へ一切加算しない。

ルールにはID、根拠、適用対象、必要データ、判定条件、欠損時の扱いを記録する。根拠未確定の条件を有効化しない。ルールが未定義であることを、適用不要や正常として扱わない。

### 7.2 2軸の表示と優先度

| 軸 | 初期版の表示 | 境界 |
| --- | --- | --- |
| データ状態 | 取得正常 / 一部未取得 / 取得失敗 / 期限切れ / デモ / 未確認 | 監視データの状態だけを表す |
| セキュリティ・トラフィックの兆候 | 判定ルール未設定 / 判定不能 / 確認範囲で兆候なし / 注意 / 要対応 | 有効なSIGNALSルールだけから決める |

SIGNALSルールが0件なら、データ状態が取得正常でも「判定ルール未設定」とする。WAFの事実表示はSIGNALSの良否判定ルールに数えない。初期版では危険度の閾値ルールを有効化しないため、取得正常だけを理由とする総合の緑色「正常」は表示しない。

将来、有効なSIGNALSルールがある場合の順序は、根拠のある要対応、注意、必須ルールの判定不能、全必須ルールを評価した上での「確認範囲で兆候なし」。必須ルール集合は事前に固定し、未設定ルールを適用外へ変換して正常にしない。

両軸には、判定不能N件（未設定ルールは別件数）、対象チェック数、欠けた項目への導線を必ず併記する。注意や要対応と欠損が混在しても、欠損件数を隠さない。任意の詳細項目の欠損は、それに依存しない主要チェックを無効化しない。

最優先操作も領域を明示する。たとえば「収集設定の確認が必要」はCOLLECTIONの操作であり、「攻撃への対応が必要」と表示しない。

### 7.3 初期版の指標別方針

| 指標 | 方針 |
| --- | --- |
| WAF処理件数 | 遮断、チャレンジ、記録等を区別。件数だけで危険・安全を決めない。現行100件の根拠未確認ルールは引き継がない |
| `/wp-login.php`等 | パスの一般的な意味と確認できた処理結果を説明する。パスだけでBot・攻撃成功・対応不要を断定しない |
| ASN・国 | アクセス元のネットワーク情報として説明。攻撃者の身元や悪意と同一視しない |
| アクセス数 | 対象期間と範囲を表示。比較対象がない状態で増加率や異常を作らない |
| キャッシュ率 | 配信効率の参考値。低いことだけでセキュリティ異常としない。母数0の率は算出不能と表示する |
| Pages利用状況 | デプロイ件数が契約上のビルド枠消費と一致するか、契約・対象・上限を確認するまで利用枠判定は未確認とする。Workersの残量へ読み替えない |

| C03 / COLLECTION | 必須。今回の検証済みerrorCode | TIMEOUT / UPSTREAM_ERROR / INVALID_RESPONSE / UNKNOWN_ERROR | 取得失敗・判定不能。「時間をおいて再取得」。エラーだけから攻撃としない |
| C04 / COLLECTION | 必須。source、status、coverage | PARTIAL、ERROR、UNKNOWN、MOCK | 部分取得・失敗・未確認・デモを区別。完全取得が必要な判定を無効化 |
| C05 / COLLECTION | 必須。validUntil、時刻基準 | 期限到達、時刻不明、期限未設定 | 期限切れまたは未確認。更新状況・収集間隔を確認する |
| W01 / FACT（良否判定外） | 有効なWAF summaryがあれば表示。actionCounts、期間、scope、sampling | APIが報告した処理種別別の件数 | 遮断・チャレンジ・記録等の事実表示とCloudflare統計の確認先。安全・危険の判定はしない |
| P01 / COLLECTION | Pagesが対象の場合。対象確認情報、一覧取得状態 | 対象・集計方法・上限が未確認、一覧途中失敗 | 利用枠未確認。確認できたデプロイ件数と契約上の残量を分ける |

優先操作はC02の設定確認、その他の取得障害・期限切れ、W01の詳細確認の順とし、同じ理由の案内をまとめる。C01の契約不正時は、入力のerrorCodeを根拠とするC02/C03を実行せず、C01の固定案内だけにする。MOCK時はデモ表示を優先し、デモ値から本番向け操作を生成しない。

失敗理由は「最後の取得試行で確認した事実」としてattemptedAtを併記する。試行時刻の鮮度が確認できない場合は、現在も同じ障害が続いているとは表示しない。C02の案内も状態の継続を断定するものではない。

レビュアー提案の前期間比は初期版で無効とする。必要になった場合は、同期間・同範囲・同じ定義・有効な両データを揃え、履歴保存と閾値の承認を別に得る。今回、継続失敗を判定する履歴も新設しない。

**提供範囲の判断は未了:** このルールセットで、取得状態に応じた操作とWAFの意味説明は提供できる。一方、元Issueのセキュリティ・トラフィック危険度の自動判定は未実現である。「この内容を初期提供として受け入れる」か「危険度ルールも初期版に必要」とするかはユーザー確認事項として残す。レビュー提案を受け取ったことだけで縮小した受入条件を承認済みとせず、元Issueを完了しない。

### 7.5 推奨アクション

同じデータ・ルール・評価時刻から同じ結果を生成する。理由に応じて「再読込する」「収集処理の設定を確認する」「Cloudflareの該当統計を確認する」等の小さな操作を示す。権限不足に対して自動的な権限拡張や、WAF無効化を提案しない。

## 8. 画面構成

1. データ状態とセキュリティ・トラフィックの兆候を並べ、それぞれの理由、判定不能件数、最優先の操作を示す。
2. データの更新状態、対象期間、対象範囲、欠けている情報。
3. 指標別の「値・意味・判断基準・次の操作」。
4. 根拠を調べるための既存グラフ・詳細一覧。

色だけで区別せず、文字とアイコンを併用する。モバイルで状態・理由・操作を先に読めるようにする。24時間統計と7日間WAFイベントは期間をそれぞれ明示し、異なる集計を割って割合を作らない。

実データの失敗や欠損を、画面側でモックや0に補完しない。明示されたモックはデモであることを常時表示し、本番の正常判定に使用しない。

日本語編集の順序は、判定根拠・説明初稿の確定、Editorial Rewrite、Semantic Fact Check、必要箇所のEditorial Fix。編集後も数値、条件、例外、未確認事項が変わっていないことを照合する。

## 10. 互換性と既存利用箇所

| 組合せ | 必須の結果 |
| --- | --- |
| 旧収集側＋新portal | 取得状態不明として扱い、正常判定しない |
| 新収集側＋新portal | 追加状態と数値を照合して判定する |
| 新収集側＋旧portal | 既存項目の構造・型を維持する。ただし旧画面の誤判定リスクは残る |
| 新portal＋収集側ロールバック | 旧形式を安全に受け入れ、判定不能へ移行する |

`ai_operations/collect_metrics.py`の最小限の同時対応を計画へ採用する。契約検証は収集側テストと共有し、Digestは旧形式、失敗、PARTIAL、デモ、期限切れのCloudflare値をnull/unavailableとする。旧数値を代替入力にしない。Pagesの契約・残量が未確認なら、旧usagePercentも利用しない。

無効値から数値異常判定を生成しないだけでなく、既存のcollector_errorsへ固定のCloudflare未取得理由を伝え、その他の重大・警告がなければ既存のpartial判定へ接続する。他サービスの有効な値や既存アラートは保持する。LLMへの入力と決定論的な表示には未取得範囲を明記し、Cloudflareを評価済みとする総括を許可しない。新しいLLMタスクは追加しない。

ローカルコード確認ではDashboardSnapshotのCloudflare値はOptionalであり、collector_errorsは全体のok/partial判定に関与する。一方、調べたevaluate_rules.pyではCloudflare値の専用閾値ルールは確認できなかった。したがって「現在すでに誤ったCloudflare異常を生成している」とは断定せず、入力と全体状態の誤解を防ぐ変更として扱う。必要なschemas/generate_digest/決定論的表示・テストの修正を最小範囲で見積もる。

収集側は既存pytest環境で対象テストを実行し、既存利用箇所の互換性も検査する。現在確認したbearworks-appsの`deploy.yml`はStreamlit検証であり、dashboardテスト成功や本番配備の証跡にはならない。必要なdashboard検証ジョブは実装段階で計画する。

portalは対象テスト、lint、通常build、LinuxのWorkers buildとpreviewを検証する。既存の認証保護、no-store、非広告境界を維持する。現在のWorkers workflowはPRまたは手動実行であり、pushやbuild成功を本番反映済みと扱わない。

## 12. 実施順序と戻し方

1. 独立計画レビューを受け、指摘と採否、未確定のルールを整理する。
2. 承認済み設計に沿って収集側とportalを実装する。同じ作業ツリーの書き手は1つに限定する。
3. 編集・意味照合、独立コードレビュー、Lunaの検証証跡、司令塔の最終確認を行う。
4. 両方の実装と検証が揃った状態で、対象commit、push、CI、配備の各操作を別に判断する。
5. 推奨順序は新portalとDigestの読取対応を先に反映し、旧形式を未確認として扱えることを確認した後、収集側の新形式を反映する。短時間の未確認表示を許容する。両repoの実装・検証を先に揃える。
6. 本番で取得状態と表示が一致することを確認し、受入条件を満たした場合だけIssueを完了する。

収集側だけを戻した場合、新portalは旧形式を判定不能として扱う。portalを旧版へ戻すと既存のモック補完・正常表示の問題も戻るため、機能の安全な撤回とは同一視しない。表示機能を止める場合は判定不能を維持する戻し方を優先し、旧画面への全面ロールバックは影響を明示して判断する。

代替の収集側先行も形式上は互換だが、旧portal・旧Digestが残る間は取得状態を無視する。先行期間を明示し、新機能の提供完了としない。推奨順では「旧形式→未確認」「新形式→契約に沿った2軸表示」を確認し、代替順では「新収集側＋旧読取側の制約」「全読取側更新後の状態一致」を確認する。具体的な順序はRelease時に司令塔が判断する。
